## 1. 目标与范围

保持“质量场景建设”为主线，复用现有质量分析系统。画像是场景资产的呈现和价值验证方式，不另建客户画像系统。

第一阶段：历史问题 → 逐问题 AI 场景解构 → 有证据的场景归纳 → 重点客户/行业的跨产品画像 → 可核查的质量短板线索。

短期从 ITR 彻底解决单切入，同时看软件与硬件；补充没有有效彻底解决单场景分析的 ITR 恢复单。机械问题保留分类和原始信息，不强制套软件分类。软件考核工作台保持软件专属，不再作为全部场景分析的唯一入口。

需要证明：问题集中在哪些客户活动；不同客户/行业/条件有什么差异；这些发现有哪些证据、哪些仍待确认。不是证明 AI 填满了多少字段。

不纳入本轮：治理任务流、部门审批、现场移动录入、自动发布、自动合并正式场景、完整装机台账、产品版本质量趋势、MTTR 计算、生产 Docker/MySQL 迁移。已有指标关联继续可用，不新增完整测试/指标管理系统。

## 3. 数据使用规则

### 3.1 现有字段的消费

| 数据来源 | 优先消费内容 | 限制 |
|---|---|---|
| 彻底解决单 | 描述、IPMT/SPDT、产品型号/编码/系列、客户/行业/分级、客户状态、原发生阶段、原因定位、TRC 纠正信息 | 流程状态不等于客户对故障的感知状态 |
| 彻底解决单硬件/机械字段 | 器件类别、失效模式、位号、编码、厂家、机理、部件/单体/产品层级 | 有字段不等于有可靠值；不能从更换后恢复直接断定器件根因 |
| ITR | 设备编码/名称、地点、产品/条码、现象、初判、发生/提单时间、使用时长、故障台数、现场记录、恢复措施/结果 | 初判不是确认根因；故障台数不是系统总规模；已用时长不是连续运行时长 |
| 漏测分析 | 已确认或有效 AI 的发生原因、流出原因、能力缺口、防控建议 | 不重复做已有诊断；未关联时显性标注“无漏测分析” |
| 软件考核 | KPI 计入月份、人工年份、软件范围、责任单位等 | 考核口径独立，不能约束硬件画像范围 |

保留原字段与原值，兼容两行表头/别名。字段映射是否已实现由 M0 核实，不直接改写原始记录。

### 3.2 权威来源与冲突

1. 问题基础事实优先彻底解决单；ITR 补现场信息和空项。同名事实冲突保留双方值、来源和待确认标记，不静默覆盖。
2. 分析结论优先有效漏测分析，其中人工确认优于未确认 AI；缺失部分再用 CS 原因定位、TRC 根因及措施。ITR 初判仍标为初判。
3. 无漏测分析时允许生成场景，但不得编造“测试为何没测出来”。
4. 逐字段记录来源记录/版本、字段、证据片段、适用对象；区分已有事实、AI 推断、信息缺失。人工确认状态独立记录，不将高置信度当成人工确认。
5. 分组是查询和分析边界。同一 ITR 跨组匹配不代表可以越组取数；仅使用用户明确纳入且规则允许的组。多个候选来源冲突不得任取一条。
6. 客户别名需确认；集团、子公司、终端客户、直接客户不自动混为一体。产品对象、问题技术领域、责任部门分别保留。

### 3.3 时间口径

软件考核视角：人工指定/批量设置的年份 + 数据运营 KPI 计入月份；未指定年份默认解析 ITR 年份。年份默认值不等于最终考核归属。

现场画像视角：优先问题发生日期，其次提单日期，并显性标注回退来源；无有效日期列为未知。若仅有明确的年/月，只按其精度统计，不伪造日期。界面可明确选择考核视角，禁止静默混合两个口径。

趋势仅称“场景问题趋势”，支持季度/半年度/年度。没有装机量、使用次数等分母，不输出故障率、质量提升率或行业风险率。

## 4. 同一问题去重与增量分析

标准单号示例：`ITR20260605084CS` 与 `ITR20260605084` 对应同一问题。仅按明确的末尾 CS 规则及格式校验归一；继承单号表示关系，不能直接合并不同问题。

| 现状 | 执行方式 |
|---|---|
| CS 已完成有效场景分析，关联 ITR 无新增有效证据 | 直接复用，ITR 不再独立调用 AI |
| CS 只有根因分析，没有场景解释 | 复用诊断，进行一次场景提取；不重做根因分析 |
| CS 与 ITR 均未完成场景分析 | 合并允许范围内证据，以标准 ITR 为一项任务 |
| 只有 ITR | 生成“现场表现与恢复”候选，根因不足明确待确认 |
| ITR 候选完成后 CS 到达 | 标记可更新，人工触发增强原候选；不新增重复资产 |
| 来源更新、词典/提示词版本变化 | 标记结果可能过期，不自动全量重跑 |
| 失败、无有效输出、冲突 | 独立状态及原因；允许仅重试失败项 |

持久化复用依据包含：允许的数据范围、标准 ITR、任务类型、有效证据指纹、词典/提示词版本。模型信息用于审计；切换模型不能自动触发所有历史问题重跑。显式重分析保留旧版本与原因。

并发任务应原子占用同一工作项，防止跨批次重复调用；中断后可恢复。人工确认/已发布资产不得被自动重跑覆盖。

每批每个输入都有台账：输入总数、归一后问题数、待处理、运行中、新生成、复用、待更新、失败、冲突、明确跳过。终态必须能对账；有未处理项不得显示全部完成。候选为零要有明确原因，不显示成功空壳。

## 5. 场景与画像语义

### 5.1 独立识别与场景归纳

逐问题识别是执行单位；稳定质量场景是资产单位，不能强制一问题一资产。多个问题归纳后仍保留行业、客户、规模、工况及证据差异。不同边界作为变体，不被一句共性描述抹掉。

跨产品客户画像是关联展示，不等于把不同产品场景自动合并为一个资产。保留现有人工同产品归纳约束。

### 5.2 活动、阶段与环境

按产品选词典及其版本，不拿 PLC 活动套全部产品。硬件可保留参与的软件业务活动，但硬件独有活动/属性需候选和确认，不强制套软件质量分类。

原问题发生阶段仅为证据：运行执行看正常任务动作；系统联动看多系统交互/时序/协同；长稳运行看持续运行或累积失效证据。不能因“在现场使用”默认运行执行，也不能因根因是编译/配置就直接归工程配置。证据不足可待定，保留备选和依据。

词典通用链路与现场实际链路分开。现场链路由证据支持；客户/行业差异可提出变体，未经确认不改通用词典。“掉电数据保持与上电恢复”应按实际触发/恢复过程判断，不被代码修改位置替代。

环境/工况包含运行状态、负载、连续运行、网络、电源、温湿度、振动、干扰等可得条件，逐条绑定对象与来源。规模包含 PLC/轴/设备/点位/客户端/工程/数据等明确数量与单位。缺失留空并解释，不补行业常识为事实。

### 5.3 客户语言与分类

保留原始长描述，同时提炼可统计的典型体验问题，例如“操作卡顿”“结果不可信”“功能用不了”“数据丢失”“恢复困难”。名称描述客户可观察后果，不用内存泄漏、线程死锁等技术根因替代。

表单/词典优先匹配；没有合适词条时 Agent 按定义、正反例、边界提出候选词及证据，人工确认后进入正式统计。禁止不断创建近义词。主体验用于单选分布，次体验可多选并注明多标签口径。

质量关注点回答客户在该活动/条件下要保证什么；正向体验要求回答期望结果；典型问题回答出了什么体验问题；质量属性回答工程归属。保留不同层次，不互相复制。软件产品质量属性沿用已确认 25010:2023 词典；使用质量模型保留独立版本标识，不混称同一版本。硬件特有属性不强行映射软件标准。

## 6. 跨产品关系的证据边界

分层展示：

- 同客户历史问题涉及的产品：仅证明共现，命名为“问题记录涉及的汇川产品”，不是完整装机清单。
- 同项目/产线/设备：需要明确项目、设备标识或原文关系证据。
- 产品交互：需要通信、控制、数据或时序交互证据；AI 推断关系单独标记，不画成已证实连线。

同型号不等于同设备；硬件问题中的工况不能传播为该客户所有软件问题的工况。客户画像可以只有产品清单和局部关系，不为好看虚构拓扑。

## 7. 第一版业务流与页面

复用场景资产入口，新增客户/行业画像视图，不替换三个工作台。

选择允许的数据组/来源 → 选择时间口径、年/月、客户/行业/产品/IPMT/SPDT → 预览独立问题数与可复用情况 → 人工触发逐问题识别 → 查看逐项结果及失败 → 人工审核 → 画像查看与证据下钻。

画像默认说明候选/已确认资产统计范围，支持切换；未发布不等于没有价值，但不能伪装正式结论。

页面优先呈现：

1. 范围与数据健康：独立问题数、来源、日期未知、缺失条件、审核状态。
2. 产品与有证据的参与关系，已知规模/环境/工况。
3. 生命周期 → 业务活动 → 典型体验问题与质量场景。
4. 客户/行业 × 活动/体验/属性矩阵，以及规模/工况对比；计数标明问题数或资产数，多标签去重口径可见。
5. 至多 3–5 条可核查发现：涉及活动与条件、问题数、典型表现、证据、反例/差异、待确认点、研发/测试讨论建议。仅计数集中只能称高频线索，不能宣布系统性根因或质量风险率。
6. 点击发现/矩阵进入来源问题及字段证据。无数据时提示缺口，不生成万能改进建议。

## 8. 开发路线与交付门禁

| 阶段 | 最小交付 | 放行条件 |
|---|---|---|
| M0 现状核对 | 路由/字段/数据流/兼容风险清单，合成回归夹具 | 明确可复用项、实际缺口，不接触内部数据 |
| M1 来源与复用 | CS/ITR 受控接入、字段证据、标准 ITR 跨批复用、独立台账 | 同问题只调用一次，分组边界与旧功能回归通过 |
| M2 场景解释增强 | 软件/硬件条件提取，产品词典、客户语言、未知/冲突、更新提议 | 不硬猜环境、不误归阶段、不覆盖人工结果 |
| M3 客户/行业画像 | 产品共现与有证据关系、矩阵、差异下钻 | 一位客户多个产品证据可追踪，不虚构系统 |
| M4 洞察与演示验收 | 有证据发现、缺口和讨论建议，状态/口径清晰 | 回答“哪里集中、何种差异、下一步核查什么” |
| M5 发布交付 | 升级包、完整包、迁移备份/回滚说明、验收记录 | 对已明确基线可升级，旧 BAT 入口不变 |

M0–M2 先完成再扩展画像；不逐阶段重复问用户是否开工。需要新权限、真实数据、业务口径选择或范围扩张时才停下确认。没有证据的测试不能标通过。

## 9. 必测场景

使用合成数据覆盖，至少包括：

1. CS + ITR + 漏测同号：一次场景任务，事实取 CS，诊断优先漏测。
2. 无漏测 CS：有候选、明确标签，不捏造流出原因。
3. ITR-only：现场恢复候选；随后 CS 导入仅产生更新提示。
4. 已完成 CS + ITR、重复点击、两个并发批次：不重复 AI 调用。
5. 59 条输入含重复/失败/复用/冲突：全部能对账，失败单独重试。
6. 同号跨隔离组、多个 CS 冲突：无越组泄漏和任意选取。
7. 来源更新、词典变更、模型切换：不静默重跑/覆盖已确认结果。
8. 软件/硬件同客户不同设备：环境不串用，关系证据不足不连线。
9. 运行、联动、长稳、掉电恢复反例：用证据区分，允许未知。
10. 产品专属词典及候选词审核：不跨产品污染，未知词不丢原文。
11. 人工年份 + KPI 月份，与发生日期不同：两种视角结果各自正确。
12. 画像下钻、旧三工作台、既有生成/审核/指标链接均可用。
13. 升级前后旧场景、人工编辑、原始数据保留；模板和依赖完整。

真实模型语义效果与 Windows BAT 验收单独记录。Mock/SQLite 通过不能冒充这两项通过。Demo 使用明确标记的合成或获准脱敏样本，不伪装实际客户结论。
