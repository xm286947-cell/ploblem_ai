# 需求池维护规则

本目录是项目需求的长期归档入口。聊天中确认但暂不开发的事项，必须进入这里，不能只保留在聊天记录或临时补丁说明中。

## 使用方式

1. 新诉求先记录到 `REQUIREMENT_INDEX.md`，分配唯一编号。
2. 范围较大的需求建立独立文件，记录背景、决策、验收条件和依赖。
3. 开发开始前把状态改为 `PLANNED` 或 `IN_PROGRESS`，并关联目标版本。
4. 完成后记录 Git 提交、测试结果和发布版本，状态改为 `DONE`。
5. 暂不实施使用 `DEFERRED`，禁止通过删除条目表示“不做”。

## 状态

| 状态 | 含义 |
|---|---|
| `IDEA` | 已记录，尚未评估 |
| `TRIAGED` | 已明确价值和大致边界 |
| `PLANNED` | 已进入版本计划 |
| `IN_PROGRESS` | 正在实施 |
| `DONE` | 已验收并发布 |
| `DEFERRED` | 有价值但当前延期 |
| `REJECTED` | 明确不实施，保留原因 |

## 优先级

| 优先级 | 含义 |
|---|---|
| `P0` | 阻断运行、数据安全或正式发布 |
| `P1` | 核心业务闭环和可信度 |
| `P2` | 重要增强，可进入后续版本 |
| `P3` | 长期规划或规模化能力 |

## 单项需求最少字段

- 需求编号、名称、状态、优先级。
- 来源日期、业务背景和用户价值。
- 当前已具备、明确缺口、不做范围。
- 数据/接口/部署影响。
- 验收条件。
- 依赖、风险、目标版本。
- 完成后的提交、测试和发布记录。
