# REQ-014 批量市场问题驱动的质量标准化

状态：`TRIAGED`

优先级：`P1`

来源：2026-08-31 标准化专题讨论

## 一、背景与目标

市场存在较多批量质量问题。一旦发生，影响范围大、整改周期长、质量损失高。标准化建设的目标不是增加文档数量，而是把已经认知清楚的质量风险转化为研发过程可复用、可验证、可准入的工程规则，减少同类问题重复发生。

核心闭环：

```text
问题
→ 认知
→ 标准
→ 设计/验证
→ 准入
→ 市场反馈
```

本专项不重新校验已有高质量问题清单，而是针对当前批量问题识别共性、控制缺口和标准建设机会。

## 二、标准识别维度

标准化不能只按使用场景分析，应同时从以下入口识别。

### 1. 使用生命周期场景

- 工程配置。
- 软件调试。
- 运行执行。
- 系统联动。
- 长稳运行。
- 版本维护：安装、升级、回退。

不同阶段的质量特性和验证要求不同，标准必须差异化。

### 2. 产品变更与非标

非标和派生产品无法全部重复完整测试，应建立：

- 差异识别。
- 影响分析。
- 风险分级。
- 验证范围。
- 结论继承规则。

核心问题是：产品发生什么变化后，哪些内容必须重新验证。

### 3. 软硬件兼容与国产化替代

底层技术栈变化但上层功能要求不变时，应独立管理兼容性风险，覆盖：

- CPU、OS、驱动。
- 数据库、中间件。
- 存储、网络。
- 应用软件版本。

输出兼容性矩阵、支持等级、代表性组合和验证要求。

### 4. 工程机理

对已有明确客观规律的问题直接沉淀工程标准，例如：

- 器件寿命和降额。
- Flash擦写和存储寿命。
- 资源上限。
- 温度和环境影响。
- 性能、容量和实时边界。

这类问题优先形成设计、选型和验证标准，不应只作为单一场景用例。

### 5. 市场问题

批量、重复、高损失和100%必现问题是最重要的标准识别入口。必现问题不能只保留在问题单或回归用例中，应进一步沉淀为设计约束、测试标准和发布准入门槛。

## 三、标准输出类型

| 标准类型 | 核心问题 |
|---|---|
| 设计标准 | 应该如何设计才能避免问题 |
| 场景质量标准 | 具体使用场景下应达到什么质量水平 |
| 验证标准 | 什么必须测、如何测、覆盖到什么程度 |
| 准入标准 | 达到什么条件才允许发布 |
| 变更/派生规则 | 哪些结论可以继承，哪些必须重新验证 |
| 兼容性规则 | 哪些软硬件组合正式支持，以及如何验证 |

一个问题可以产生多个标准建议，但必须区分主标准类型和辅助标准类型。

## 四、软件标准化分析模型

软件质量标准按以下结构表达：

```text
使用场景 × 质量特性 × 边界条件 × 验证方式
```

示例：

- 工程配置 × 容量。
- 软件调试 × 可诊断性。
- 运行执行 × 性能。
- 系统联动 × 实时性/容错。
- 长稳运行 × 资源稳定性。
- 版本维护 × 兼容性/升级恢复。

整体定义：以使用生命周期为主线，结合产品变更、兼容性和工程机理，建立差异化的软件质量标准。

## 五、单问题标准识别问题集

分析每个批量问题时，统一回答：

1. 是否批量、重复、高损失或必现？
2. 发生在哪个使用生命周期阶段？
3. 是否由非标、设计变更或器件替代导致？
4. 是否与国产化或软硬件兼容有关？
5. 是否存在明确工程机理或客观边界？
6. 过去为什么没有被设计、测试、评审或准入环节拦截？
7. 应转化为设计、场景、验证、准入、变更还是兼容性标准？
8. 建议标准如何验证已经产生预防效果？

## 六、专项分析输出契约

每个问题或共性问题簇至少输出：

| 字段 | 说明 |
|---|---|
| 问题/问题簇 | 原问题与聚类标识 |
| 批量影响 | 数量、范围、损失和客户影响 |
| 触发条件 | 问题出现所需条件 |
| 根因/工程机理 | 已确认事实与待确认推断分开记录 |
| 生命周期场景 | 配置、调试、运行、联动、长稳或版本维护 |
| 产品变化 | 非标、设计变更、器件替代和版本组合 |
| 兼容性因素 | CPU、OS、驱动、数据库、中间件、存储、网络和应用版本 |
| 现有控制 | 已有设计、测试、评审和准入措施 |
| 控制缺口 | 为什么未被提前预防或拦截 |
| 是否可标准化 | YES、PARTIAL、NO、INSUFFICIENT_INFO |
| 标准类型 | 主类型和辅助类型 |
| 建议标准内容 | 设计约束、边界、验证方法和准入条件 |
| 优先级 | 综合批量影响、再发风险、可复用性和实施成本 |
| 证据与置信度 | 来源、证据、AI推断和人工确认状态 |

## 七、专项业务流程

```text
选择当前批量问题数据集
→ 数据质量和分析覆盖预检
→ 单问题标准识别
→ 共性失效模式聚类
→ 标准缺口归并
→ 专家人工评审
→ 形成标准候选池
→ 进入设计/验证/准入流程
→ 跟踪市场问题和质量损失变化
```

## 八、系统能力建议

### 数据集分析

复用 REQ-013 的隔离数据集，批量问题专项默认不污染现有正式质量洞察。支持针对单一数据集运行标准化分析和生成专项报告。

### 标准候选池

新增标准候选对象，至少具备：

- 标准候选编号、名称和类型。
- 来源问题、问题簇和适用产品。
- 使用场景、质量特性和边界条件。
- 建议设计约束、验证方法和准入门槛。
- 责任人、评审人、优先级和状态。
- 证据、置信度和人工确认记录。
- 关联的正式标准、版本和生效范围。

建议状态：

```text
DRAFT
→ REVIEW_REQUIRED
→ APPROVED
→ STANDARDIZED
→ IMPLEMENTED
→ VERIFIED
→ RETIRED
```

### 标准效果验证

标准发布不是完成条件。需要持续验证：

- 同类问题是否减少。
- 批量质量损失是否降低。
- 设计和测试活动是否真正执行。
- 准入门槛是否拦截风险。
- 新产品和派生产品是否复用。

## 九、与现有系统的关系

- 现有问题清单仍是事实来源，不重新制造第二套问题事实。
- 现有发生/流出、能力缺口、生命周期、硬件关联和人工确认可作为输入。
- REQ-013负责低质量批量数据的分组、隔离和分析范围。
- REQ-014负责从批量问题识别标准缺口、形成标准候选并验证效果。
- 产品质量报告回答“产品主要矛盾”；标准化专项报告回答“哪些矛盾应转化为什么标准”。

## 十、MVP范围

第一阶段不扩展完整标准管理平台，只完成一次真实数据实证：

1. 选择一个当前批量问题数据集。
2. 按统一输出契约完成分析。
3. 形成共性失效模式和标准候选清单。
4. 由质量、研发和测试专家人工评审。
5. 根据实证结果冻结最终分类框架和Prompt。

## 十一、验收条件

1. 每个结论可下钻到真实问题和证据。
2. AI推断与客观事实、人工确认明确区分。
3. 能识别场景、变更、兼容性和工程机理等不同标准入口。
4. 输出至少覆盖设计、场景、验证、准入、变更和兼容性标准类型。
5. 能按影响、再发风险、复用范围和实施成本形成优先级。
6. 专家能够据此决定“进入标准建设、补充证据或不标准化”。
7. 数据集分析不污染正式质量洞察。
8. 形成一份真实批量问题标准化专项报告和标准候选清单。
