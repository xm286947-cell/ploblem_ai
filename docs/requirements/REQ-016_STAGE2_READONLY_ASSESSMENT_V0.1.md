# REQ-016 第二阶段只读准备评估 V0.1

日期：2026-08-31

## 1. 结论

当前可以进入第二阶段的“指标口径与真实数据核对”，但还不能进入正式 MTTR 看板开发。

原因是当前仓库可见样本主要是漏测分析数据，不是完整的 ITR 运行过程数据：

- 已有 ITR 编号、月份、严重程度、产品、问题描述、原因、措施和重复问题等字段；
- 没有可验证的发生、受理、首次响应、开始定位、临时恢复、根因确认、永久措施完成、验证和关闭时间链；
- 当前运行数据库文件 `knowledge/quality_capability_p1.db` 为空，无法从数据库计算真实字段完整率；
- `input/new_cases.xlsx` 是查询案例样本；`plc_quality_issue_full_fields_e2e.xlsx` 是漏测分析 E2E 样本，均不能代表真实 ITR 时间数据。

因此，现阶段若直接计算 MTTR，只能产生伪精确指标。

## 2. 当前已具备的可复用能力

### 2.1 关联与去重基础

- 已能映射 ITR 单号及常见别名；
- 现有问题实体可按业务问题编号查询；
- 同一问题支持多版本；
- 原始 Excel 数据和标准化数据均可保留；
- ITR 编号已支持解析提交年份和月份，并允许人工覆盖结算年月。

### 2.2 可直接用于运行洞察的字段

- ITR 编号；
- 年、月；
- 产品、平台、产品系列、模块；
- 严重程度、问题类型；
- 客户、部门、业务组；
- 问题领域；
- 是否历史同类问题；
- 原因分类和流出分类；
- 纠正、预防及改进措施。

### 2.3 可复用页面能力

- 问题工作台筛选、分页和精确下钻；
- 产品、月份、严重程度和领域筛选；
- 原始数据与标准化数据查看；
- 质量洞察聚合与关联问题下钻。

第二阶段应复用这些能力，不重做现有前端和问题分析流程。

|---|---|---|---|
| 问题发生 | 客户现场首次发生时间 | 全链路起点 | 未发现 |

| 首次响应 | 责任团队首次有效响应时间 | 首响时长 | 未发现 |
| 开始定位 | 开始技术定位时间 | 定位等待时间 | 未发现 |
| 临时恢复 | 客户业务恢复时间 | 现场恢复时长 | 未发现 |
| 根因确认 | 根因得到证据确认的时间 | 根因定位时长 | 未发现 |
| 永久措施完成 | 修复或彻底措施完成时间 | 彻底解决时长 | 未发现 |

## 4. 建议的指标口径草案

以下只是待业务确认的候选口径，不作为当前正式计算规则：

| 指标 | 起点 | 终点 | 说明 |
|---|---|---|---|
| 登记延迟 | 问题发生 | ITR创建/受理 | 反映现场问题登记及时性 |
| 首次响应时长 | ITR创建/受理 | 首次响应 | 反映组织响应效率 |
| 定位启动时长 | 首次响应 | 开始定位 | 反映技术资源投入效率 |
| 现场恢复时长 | 问题发生 | 临时恢复 | 建议作为现场恢复 MTTR |
| 根因确认时长 | 问题发生 | 根因确认 | 反映定位效率 |
| 永久解决时长 | 问题发生 | 永久措施完成 | 反映彻底解决效率 |
| 验证关闭时长 | 永久措施完成 | 问题关闭 | 反映验证和关闭效率 |
| 完整闭环时长 | 问题发生 | 问题关闭 | 反映端到端闭环效率 |

“MTTR”必须明确指现场恢复还是彻底解决，页面不能只展示一个无定义的 MTTR。

## 5. 数据质量与异常规则草案

1. 时间缺失：该分段指标记为不可计算，不以零代替。
2. 负时长：标记为时间顺序异常，排除出有效样本。
3. 仅有日期：允许按天统计，不与精确到分钟的时长混合宣称精度。
4. 多次恢复：保留首次恢复和最终稳定恢复，不能任意覆盖。
5. 问题重新打开：单独记录重开次数；完整闭环以最终关闭为终点。
6. 暂停等待客户：总历时和净处理时长分开，未取得暂停区间前只计算总历时。
7. 异常长时长：先按分位数展示并下钻，不在业务确认前硬编码阈值。
8. 重复 ITR：按 ITR 编号统计一次，多份材料不得放大问题数。
9. 人工修改：必须保留原始值、修改值、修改人、时间和原因。

## 6. 最小开发清单

指标口径确认后，建议只实施以下最小增量：

1. 扩展字段映射，使真实 ITR 时间字段可配置导入；
2. 增加时间值规范化、完整度和异常校验；
3. 增加只读指标服务，统一输出分段时长、有效性和计算依据；
4. 在现有质量洞察增加独立的“质量运行”区域，不替换当前深度分析洞察；
5. 支持按产品、年月、严重程度、发生阶段和领域筛选；
6. 汇总值能够精确下钻到 ITR；
7. 页面固定显示总样本数、有效样本数、完整率和异常数；
8. 增加真实样本回归测试和边界数据测试。

## 7. 开发门与下一步输入

进入代码开发前，需要一份脱敏的真实 ITR 导出样本，并至少包含：

- 完整表头；
- 若干正常闭环问题；
- 一个仍未恢复或未关闭的问题；
- 一个时间缺失问题；
- 一个重开或多次恢复问题（若业务存在）；
- 严重程度和发生阶段字段。

拿到样本后，先输出：

1. 字段含义及别名对照；
2. 每个时间字段完整率；
3. 时间顺序异常率；
4. 五类分段指标的可计算率；
5. 三至五条人工可复核的计算样例。

业务确认上述结果后，再进入正式开发。
