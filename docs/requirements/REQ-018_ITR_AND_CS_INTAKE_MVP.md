# REQ-018 ITR与彻底解决单接入、自动关联和统一问题视图

状态：READY

优先级：P0

阶段：短期MVP

## 1. 目标

在不改变现有漏测分析业务流程的前提下，新增 ITR 问题、ITR 彻底解决单和软件问题运营数据的独立接入、分组隔离、查询、详情展示和可配置关联能力。

短期只建立完整的问题链路，不提前实现 MTTR 正式公式、管理看板或新的 AI 深度分析。

## 2. 业务范围

### 2.1 ITR问题

- 独立导入 ITR Excel；
- 支持两级表头合并识别；
- 保留所有原始字段；
- 支持映射、预检、导入、去重和更新；
- 支持按 ITR 编号、产品、严重程度、发生阶段、年月和状态查询；
- 支持软件、硬件、机械、跨领域和待确认领域属性；
- 详情展示问题事实、客户与产品、发生信息、过程信息、时间信息和处理结果。

### 2.2 ITR彻底解决单

- 独立导入彻底解决单 Excel；
- 保留所有原始字段；
- 展示责任认定、分流、技术根因、纠正措施、根因审核、MRC判定、复盘与标准化过程；
- 保留软件模块、硬件器件及机械失效字段；
- 支持彻底解决状态、超期状态、MRC状态和标准化状态查询。

### 2.3 软件问题运营数据

该数据是彻底解决单部分字段形成的运营考核快照，主要用于KPI和责任考核，不作为新的技术根因权威来源。

- 通过彻底解决单号关联CS及原始ITR；
- 独立保存审核状态、是否IFA平台问题、KPI计入月份、责任单位1/2和KPI考核类型；
- 保留问题基本信息、责任认定、流程状态、纠正措施状态及软件失效分类；
- 支持软件平台、软件模块、软件功能、产品层级软件失效模式和功能层级软件失效机理；
- 与CS不一致时显示差异，不得反向覆盖CS；
- 默认不进入AI分析、现有质量洞察和产品综合报告。

## 3. 自动关联规则

标准编号示例：

```text
ITR问题单：ITR20260605084
彻底解决单：ITR20260605084CS
```

规则：

1. 清除编号首尾空格并统一为大写；
2. 彻底解决单号仅在末尾为 `CS` 时去除该后缀；
3. 使用去除 `CS` 后的编号匹配唯一 ITR；
4. 原始 ITR 编号和彻底解决单号均完整保留；
5. 关联不能覆盖或修改源数据；
6. 问题数量按 ITR 编号去重，CS单不单独增加问题数。

上述 `ITR + CS` 是系统可提供的默认关联规则，但不得作为唯一的硬编码关联方式。

关联状态：

- `LINKED`：找到唯一 ITR；
- `ITR_NOT_FOUND`：CS编号有效，但基础ITR尚未导入；
- `CS_NOT_STARTED`：ITR尚无彻底解决单；
- `INVALID_NUMBER`：编号格式异常；
- `CONFLICT`：出现重复或非唯一关系；
- `MANUAL_LINKED`：人工确认的例外关联。

### 3.1 漏测分析与原始问题关联

当前漏测分析数据应支持自动关联 ITR 原始问题及对应的彻底解决单。

默认建议链路：

```text
漏测分析.ITR单号
→ ITR原始问题.问题信息_ITR单号
→ ITR彻底解决单.问题信息_彻底解决单号（ITR单号 + CS）
```

关联后，在同一问题视图中可以查看：

- ITR现场事实和处理过程；
- 漏测分析中的开发、测试分析；
- 彻底解决单中的技术根因、永久措施、MRC和标准化过程。

漏测分析没有匹配到原始 ITR 时仍可独立存在，并标识“原始问题待关联”，不能阻止现有业务使用。

### 3.2 关联配置能力

系统应允许业务管理员配置哪些数据之间建立关联，至少包括：

- 来源数据类型；
- 来源业务字段；
- 目标数据类型；
- 目标业务字段；
- 匹配方式：精确匹配、去空格、忽略大小写、前后缀转换；
- 是否启用；
- 规则优先级；
- 是否允许一对多；
- 冲突时停止、待确认或采用人工关联；
- 是否对历史已导入数据执行补关联。

首批内置规则：

1. 漏测分析 ITR单号 → ITR原始问题 ITR单号；
2. ITR原始问题 ITR单号 → 彻底解决单号（追加 `CS`）；
3. 彻底解决单号 → ITR原始问题 ITR单号（移除末尾 `CS`）。
4. 软件问题运营数据彻底解决单号 → ITR原始问题 ITR单号（移除末尾 `CS`）。

规则必须支持草稿、预检、启用、停用和版本记录。启用前应展示预计匹配数、未匹配数和冲突数。

## 4. 数据分组与隔离

### 4.1 基本要求

每次导入必须选择或创建数据分组。数据分组用于控制数据的业务范围、默认查询范围和分析范围，不能只作为显示标签。

短期至少预置：

- `ESCAPE_ANALYSIS`：现有漏测分析数据；
- `ITR_SOURCE`：ITR原始问题数据；
- `ITR_CS`：ITR彻底解决单；
- `SOFTWARE_OPERATION`：软件问题运营与考核数据；
- `BATCH_ISSUE`：批量问题，保留但本期不开发专项分析；
- `TEST_ISSUE`：测试问题，保留但本期不开发专项分析。

### 4.2 隔离原则

- 各分组分别导入、查询、统计和导出；
- 默认统计与AI分析只读取明确选择的数据分组；
- 新增 ITR/CS 默认不进入现有漏测分析洞察和产品综合报告；
- 分组之间通过关联关系互相查看，不通过物理混合实现；
- 同一条源数据必须明确属于一个主分组；
- 支持按导入批次继续细分，便于低质量数据隔离和撤销；
- 页面始终显示当前数据分组和统计口径；
- 后续可以配置某分组是否允许AI分析、是否进入洞察、是否进入正式报告。

### 4.3 分组管理最小能力

- 新建、启用、停用数据分组；
- 配置中文名称、业务说明和数据类型；
- 查看数据量、最近导入时间和导入批次；
- 设置默认查询、AI分析、洞察和报告范围；
- 停用分组不删除数据；
- 已有关联不因分组停用而丢失。

## 5. 统一问题视图

### 5.1 独立工作台

三类数据必须形成三个独立工作台，而不是在一个通用材料页中仅靠下拉框切换：

1. **ITR问题工作台**：现场问题、客户影响、发生阶段、处理过程；领域覆盖软件、硬件、机械和跨领域。
2. **ITR彻底解决工作台**：责任认定、技术根因、永久措施、MRC与标准化；领域覆盖软件、硬件、机械和跨领域。
3. **软件问题考核工作台**：审核状态、KPI月份、责任单位、考核类型及软件失效分类；范围仅限软件。

三个工作台分别导入、筛选、统计和导出，并为将来的独立分析保留边界。工作台之间通过ITR关系跳转，不共享默认统计口径。

### 5.2 关联后的统一详情

同一 ITR 详情页按业务分区展示：

1. ITR现场问题；
2. 现场处理过程；
3. 漏测分析（存在关联时）；
4. 彻底解决单；
5. 软件问题运营与考核快照；
6. 技术根因与永久措施；
7. 根因审核与MRC判定；
8. 复盘与标准化状态；
9. 各分组原始数据及来源；
10. 关联规则、关联状态和异常说明。

页面复用现有详情页的信息密度、导航、原始数据展示和中文UED风格，不重新建设独立视觉体系。

## 6. 现有功能影响

- ITR、CS、软件运营和当前漏测分析数据明确标识材料类型；
- 新增数据默认不进入现有漏测分析统计、能力缺口聚合和产品综合报告；
- 当前问题工作台、批量AI分析、人工分析、质量洞察和字段映射流程不得退化；
- 后续需要将ITR纳入MTTR或其他洞察时，另行启用明确的数据范围；
- 不要求兼容未使用的历史试验数据，但不得破坏当前稳定包已有数据。

## 7. 短期不实施

- MTTR、SLA和OLA正式计算公式；
- ITR质量运行管理看板；
- ITR批量AI深度分析；
- 重大问题、批量问题和测试问题接入；
- 标准成果库和标准发布流程；
- 任意复杂多对多关联；
- Docker/MySQL正式部署改造。

## 8. 开发顺序

1. 获取脱敏 ITR 与CS样本，确认两级表头和数据格式；
2. 建立数据分组及其查询、分析和统计隔离规则；
3. 建立两类材料的字段目录及最小公共字段；
4. 完成独立导入、预检、原始数据保留和导入诊断；
5. 完成关联规则配置、预检、启用和历史补关联；
6. 完成编号规范化与三类数据自动关联；
7. 完成列表、筛选和统一问题详情；
8. 使用真实样本执行导入、关联、更新、隔离和异常场景回归；
9. 生成补丁包和合并后的完整包。

## 9. 验收条件

1. 两级表头可以正确合并，原始字段无丢失；
2. ITR和CS可分别导入、查询和查看原始数据；
3. `ITR20260605084CS`可自动关联到`ITR20260605084`；
4. 导入顺序不影响最终关联，先导CS后导ITR也能补关联；
5. 同一ITR重复导入不会重复增加问题数；
6. 更新ITR或CS时保留版本和来源信息；
7. 编号异常、缺失、重复和冲突均有可理解的诊断信息；
8. 一个问题详情能够同时查看ITR和CS材料；
9. 新增数据不污染现有漏测分析洞察；
10. 每次导入均明确选择数据分组，各分组查询和统计互不污染；
11. 漏测分析可根据启用的规则自动关联原始ITR和CS；
12. 关联规则启用前能预检匹配、未匹配和冲突数量；
13. 新规则可以对历史数据安全补关联；
14. 停用或修改规则不会删除原始数据，历史关系可追溯；
15. 现有稳定功能专项回归全部通过。
