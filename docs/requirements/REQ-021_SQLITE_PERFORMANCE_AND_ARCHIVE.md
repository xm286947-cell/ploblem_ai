# REQ-021 SQLite 大库性能、体检、查询分页与历史运行数据归档

状态：TRIAGED  
优先级：P0  
建议阶段：近期独立性能专项  
记录日期：2026-09-06

## 一、背景

当前 Win10 本地测试仍采用 SQLite，并通过 BAT 启动。用户反馈实际运行数据库已超过 600 MB，部分工作台查询明显变慢。

当前 Mac 开发目录没有可用于容量分析的真实 Windows 运行数据库，因此现阶段只能确认代码层风险，不能凭文件总大小判断具体由哪张表、哪类数据占用。实施前必须先对真实数据库生成只读体检报告。

## 二、已确认的代码层风险

1. 部分工作台先读取最高 100000 条完整原始 JSON，再在 Python 中筛选、分页和统计。
2. 场景清单及范围选项存在整表加载、逐条解析 JSON、重复构造视图的路径。
3. 同一问题可能同时保存原始材料、标准化版本、子表数据、AI 结果以及调试输入输出，长期分析会持续累积。
4. 当前索引主要覆盖少量编号和类型字段，分组、年月、报告年份、状态和常用组合筛选缺少针对性验证。
5. 尚未形成面向用户的数据库体检、历史运行数据保留周期和安全维护机制。

## 三、目标

- 普通清单查询由数据库完成筛选、排序和分页，页面只读取当前页需要的字段。
- 高频筛选建立经过真实查询计划验证的索引，避免盲目堆索引。
- 原始业务数据、正式分析结果和可删除的运行/调试数据分层管理。
- 提供只读体检结果：表大小、行数、索引、查询耗时、历史运行数据占比和可回收空间。
- 在不改变 BAT 使用入口的前提下，支持安全备份、优化、归档和回滚。
- 设计时兼顾未来 Linux + MySQL 部署，避免把新增查询逻辑锁死在 SQLite 特性上。

## 四、分阶段实施

### P0：真实数据库只读体检

- 在 Windows 实际数据库上统计各表行数、页数和主要大字段占用。
- 识别最慢页面及对应查询，记录基准耗时和查询计划。
- 区分业务原始数据、正式资产、AI 运行记录、调试记录及可再生成缓存。
- 只输出报告，不删除、不压缩、不迁移数据。

### P1：无损查询优化

- 将材料清单、软件考核工作台、质量场景清单和常用筛选改为 SQL 分页与字段投影。
- 对分组、数据类型、状态、ITR 编号、报告年份、KPI 月份、IPMT、SPDT、产品型号等常用条件验证并补充索引。
- 避免列表页读取和解析不需要的完整 `raw_json`、分析结果和调试报文。
- 缓存或预聚合变化频率低的筛选项和统计项，并明确刷新条件。
- 统一连接参数及安全的 SQLite 优化配置，保留兼容回退方式。

### P2：历史运行数据归档与维护

- 为 AI 调试输入输出、重复运行记录、失败任务明细和可再生成缓存定义保留周期。
- 提供“先预览、再备份、后归档”的人工触发流程，显示预计释放空间和影响范围。
- 原始问题数据、正式发布场景、人工分析、关联关系和审计证据默认不得删除。
- 数据库压缩只能在停机、完成备份且空间充足时执行，禁止在线直接运行高风险压缩操作。

## 五、验收标准

- 使用真实 600 MB 以上数据库完成优化前后对比，并保存测试记录。
- 常用列表首屏目标不高于 1 秒，复杂组合筛选目标不高于 2 秒；未达到时必须列明瓶颈。
- 分页接口读取量与当前页规模同量级，不再固定扫描 100000 条完整记录。
- 优化和归档前后，原始问题数、正式场景数、问题关联数和人工结论校验一致。
- BAT 启动入口、SQLite 本地调试方式和现有页面地址保持兼容。
- 任一归档或维护动作均有备份、操作日志和明确回滚路径。

## 六、本轮边界

本需求仅归档，当前不直接修改真实数据库，不执行删除、VACUUM、迁移或覆盖操作。待能访问公司环境和实际数据库后，从 P0 只读体检开始。
