# REQ-007 正式环境升级与回滚

状态：`TRIAGED`  
优先级：`P0`  
来源：2026-08-30 上线升级规划

## 核心原则

上线后禁止直接覆盖源码或叠加零散补丁，统一采用：

```text
版本化 Docker 镜像
+ 数据库版本迁移
+ 持久化数据卷
+ 升级前备份
+ 健康检查
+ 可回滚发布
```

## 数据边界

| 内容 | 保存方式 | 升级行为 |
|---|---|---|
| 应用代码 | Docker 镜像 | 替换镜像 |
| MySQL 数据 | 持久化卷/外部服务 | 不随容器删除 |
| Excel/PDF/证据附件 | 独立卷或对象存储 | 不随镜像覆盖 |
| 配置 | 环境变量/挂载配置 | 保留并校验 |
| Prompt/词典/Mapping | 版本化配置或数据库 | 受控迁移 |
| 日志 | 独立日志卷 | 保留并轮转 |
| 密钥 | Secret/环境变量 | 不进入镜像 |

## Release Bundle

每个正式版本统一交付：

```text
docker-compose.yml
.env.example
images/*.tar
migrations/
upgrade.sh
rollback.sh
backup.sh
verify.sh
RELEASE_NOTES.md
MANIFEST.json
```

支持无互联网环境通过 `docker load` 离线安装镜像。

## 标准升级流程

```text
预检
→ 阻止新分析任务
→ 等待运行任务完成或保存检查点
→ 备份 MySQL、附件和配置
→ 执行向前兼容数据库迁移
→ 启动新镜像
→ 健康检查
→ 核心业务冒烟测试
→ 恢复任务
→ 记录升级结果
```

## 数据库策略

采用“扩展—切换—清理”：

1. 先新增表/字段，不立即删除旧结构。
2. 新旧应用短期均能读取。
3. 数据迁移并验证后切换新逻辑。
4. 稳定至少一个发布周期后再清理废弃结构。

## 回滚

### 应用回滚

数据库仍兼容时，直接切回上一版本镜像。

### 数据回滚

数据库已产生不兼容变化时：停止服务，恢复升级前 MySQL 与附件快照，然后启动旧镜像。不得只回滚镜像而忽略数据结构。

## AI任务保护

- 升级前进入维护模式，不接受新任务。
- 运行任务应完成、暂停或持久化检查点。
- 新版本恢复未完成任务时不得重复写入结果。
- 每次分析记录应用、Prompt、Schema、模型和分析引擎版本。

## 版本与发布说明

采用 `主版本.功能版本.修复版本`。每个版本必须声明：

- 最低可升级版本。
- 数据库/API/配置变化。
- 是否需要重新分析历史问题。
- 是否支持直接应用回滚。
- 停机窗口。
- 备份、迁移、验证和回滚步骤。

## 验收条件

1. 升级脚本可重复执行且具有幂等保护。
2. 升级前自动生成可验证备份。
3. 健康检查失败时停止切换并给出恢复动作。
4. 最近两个版本镜像可用。
5. 应用回滚和数据库恢复各完成一次演练。
6. 升级前后核心数据数量、关联完整性和关键业务结果一致。
7. 升级过程、操作者、版本和结果可审计。
