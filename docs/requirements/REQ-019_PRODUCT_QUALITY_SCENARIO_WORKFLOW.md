# REQ-019 客户问题逆向推理与产品质量场景库

## 1. 目标

基于已有客户问题、ITR彻底解决单和漏测分析数据，通过多证据推理将历史问题映射到统一的使用生命周期、业务活动场景和场景链路，再由人工选择问题范围、触发AI聚类和审核，形成可复用、可溯源、可版本化的产品质量场景资产。

核心链路：

```text
彻底解决单问题事实
+ 漏测问题高质量分析（若已关联）
+ TRC纠正信息
+ 生命周期与业务活动词典
→ 单问题场景推理
→ 人工选择问题范围
→ AI聚类并生成场景候选
→ 人工审核、合并、拆分
→ 发布产品质量场景库
```

## 2. 分类词典基线

首版参考《`iFA_Evolution_PLC_使用生命周期与业务活动场景.xlsx`》：

- 6个生命周期：工程配置、软件调试、运行执行、系统联动、长稳运行、版本维护；
- 34个业务活动场景；
- 每个场景已有场景链路、价值与描述、目标。

该文件是 iFA Evolution（PLC）业务词典，不直接当作所有产品的通用词典。后续HMI、机器人及其他软件产品可共用6个一级生命周期，但应维护自己的业务活动场景。

词典正式入库前必须补充：

- `lifecycle_code`、`activity_code`稳定编码；
- 中文名、定义、场景链路和目标；
- 适用产品与问题领域；
- 典型动作、对象、触发条件和可观察结果；
- 历史别名；
- 正例、反例和易混淆场景边界；
- 版本、状态、创建人和激活时间。

### 2.1 词典可维护性

生命周期和业务活动场景必须支持在系统中修改，不将Excel或代码固定枚举作为唯一来源。

管理能力至少包含：

- 新增、修改、启用和停用生命周期；
- 新增、修改、启用和停用业务活动场景；
- 维护场景名称、定义、场景链路、目标、典型证据、别名、正例、反例和判定边界；
- 配置适用的IPMT、SPDT、产品型号和问题领域；
- 从Excel导入词典草稿，导入前预览差异；
- 校验编码重复、层级断裂、必填字段和正反例缺失；
- 草稿预览、激活、回滚和版本对比。

版本规则：

- `DRAFT` 版本可编辑；
- `ACTIVE` 版本已被分析引用后不原地修改，再次修改产生新草稿版本；
- 每条单问题分析和已发布质量场景保留当时使用的词典版本；
- 激活新版本不自动改写历史分析，由人工选择是否重新分析。

## 3. 数据权威与合并规则

### 3.1 彻底解决单提供的事实

首版仅将以下字段纳入场景推理的事实上下文：

- 问题信息：问题描述、IPMT、SPDT、产品型号、客户行业、客户名称、客户分级、当前问题状态、问题发生阶段、问题原因定位；
- 技术根因分析与纠正：TRC纠正信息。

字段语义：

- IPMT、SPDT是业务组织的上下级归属，用于组织范围筛选，不当作产品层级；
- 当前问题状态表示客户对故障的感知和恢复程度，如易用性问题、复位可恢复、重启可恢复、持续故障，不等于流程审批状态；
- TRC纠正信息用于反向校验真实修改对象、根因和改进措施。

### 3.2 关联后的权威矩阵

| 信息类型 | 主值来源 | 说明 |
|---|---|---|
| 问题事实、客户及产品信息 | ITR彻底解决单 | 问题描述、产品、行业、客户、感知状态等 |
| 原始问题发生阶段 | ITR彻底解决单 | 仅是推理证据，不是最终标准阶段 |
| 根因、流出原因和测试未发现原因 | 漏测分析 | 关联成功时以其高质量分析为准 |
| 质量工程、质量管理和治理能力缺口 | 漏测分析 | 使用有效AI结果及人工修订 |
| 人工确认结论 | 漏测人工分析 | 高于AI原始结果 |
| 技术纠正和最终措施 | ITR彻底解决单TRC纠正信息 | 用于校验问题本质和标准化方向 |

合并原则：

- 不物理合并或反向覆盖原始数据；
- 在关联视图中按权威矩阵选择主值；
- 每个字段保留 `source_type`、`source_record_id`和 `source_field`；
- 两侧冲突时显示主值、参考值和“数据差异”，不静默覆盖；
- 完全没有漏测分析时，可完成事实与场景推理，但必须标记“无漏测分析”，不输出测试流出原因和完整能力缺口。

## 4. 单问题场景推理

### 4.1 输入

- 彻底解决单的指定事实字段；
- 按ITR编号关联到的漏测分析有效结论；
- 人工确认和修订；
- 当前激活的产品、生命周期和业务活动词典版本。

### 4.2 固定输出合同

```text
standard_lifecycle:
  code, label_zh, original_value, rationale, confidence
business_activity:
  code, label_zh, chain_node, rationale, confidence
reconstructed_context:
  user_role, system_objects, scale, environment,
  preconditions, key_action, trigger_conditions,
  observed_failure, customer_impact
customer_quality_experience:
  experience_requirement, concern_points[]
quality_attributes[]:
  standard, category, subcategory, rationale
evidence[]:
  source_type, source_record_id, source_field, excerpt
alternatives[]:
  lifecycle_code, activity_code, excluded_reason
confirmation_questions[]:
  question_key, question_text, priority, target_path
metadata:
  taxonomy_version, prompt_version, model_name,
  input_hash, analysis_time
```

约束：

- 推理结果与原始值分开存储；
- 每项关键结论至少有一条证据；
- 不能确定的字段输出 `UNKNOWN`，不硬猜；
- 阶段与活动低置信度时必须产生待确认问题；
- 必须输出至少一个“未选其他候选场景”的排除理由；
- 不把原始发生阶段直接复制成最终分类。

### 4.3 关键判定边界

1. **软件调试 vs 长稳运行**：出现在调试现场不等于软件调试；若依赖长时间、累积量、高负载或反复恢复，优先候选长稳运行。
2. **运行执行 vs 系统联动**：单PLC内部任务、程序、状态和数据处理属运行执行；涉及PLC与其他设备或系统的交互闭环属系统联动。
3. **工程配置 vs 版本维护**：首次创建、组态、参数和程序开发属工程配置；已交付系统的升级、迁移、替换、修改、备份恢复和回退属版本维护。

## 5. 人工指定的场景库生成流程

场景库生成不自动运行，不因单问题AI分析完成而自动发布。

### 5.1 流程

1. 在彻底解决工作台选择产品、时间、IPMT、SPDT、客户行业、问题等级和场景分析状态；
2. 人工勾选本次参与生成的问题；
3. 系统固化本次选择范围、词典版本和输入快照；
4. 用户点击“生成场景候选”，AI按阶段、活动、客户体验和失效表现聚类；
5. 展示聚类依据、候选场景、来源问题、异常点和待确认项；
6. 人工修改场景名称、合并或拆分聚类、移动来源问题、补充适用边界、指标和验证方向；
7. 人工审核后发布到场景库；
8. 后续重新分析生成新候选版本，不覆盖已发布版本。

### 5.2 状态

```text
单问题：NOT_ANALYZED / RUNNING / REVIEW_REQUIRED / CONFIRMED / FAILED
生成任务：DRAFT / READY / RUNNING / REVIEW_REQUIRED / COMPLETED / FAILED
场景资产：CANDIDATE / IN_REVIEW / PUBLISHED / RETIRED
```

## 6. 产品质量场景资产

发布对象至少包含：

- 场景编码、名称和版本；
- 适用产品、领域、生命周期和业务活动；
- 场景链路与问题节点；
- 用户角色、系统/设备对象、环境、规模、前置条件和关键操作；
- 触发条件、可观察异常和客户影响；
- 客户质量体验要求与质量关注点；
- 工程质量属性；
- 适用范围和排除边界；
- 候选指标、阈值状态和验证方向；
- 来源问题关系及每条问题的聚类理由；
- 审核人、发布人和发布时间。

## 7. 页面设计

### 7.1 彻底解决工作台

在现有查询工作台增加：

- IPMT、SPDT、产品、时间、客户行业、客户分级、当前问题状态筛选；
- 关联状态、场景分析状态和置信度列；
- 批量勾选、“分析选中问题”和“生成场景候选”；
- 页面顶部始终显示数据范围和词典版本。

### 7.2 关联问题详情

信息顺序：

1. 彻底解决单问题事实；
2. 标准生命周期、业务活动、场景链路及证据；
3. 漏测问题根因、流出原因和能力缺口；
4. TRC纠正信息；
5. 客户质量体验和质量属性；
6. AI待确认项与人工修订；
7. 原始数据和技术追溯。

所有主结论都显示来源、证据和置信度。

### 7.3 场景候选工作台

- 左侧：聚类列表、问题数、置信度和差异诊断；
- 中间：场景候选内容、适用范围、客户体验、指标和验证建议；
- 右侧：来源问题及匹配理由；
- 支持合并、拆分、移动问题、退回重分析和提交审核；
- 发布前检查场景名称、范围、证据、来源问题和验证方向。

### 7.4 已发布场景库

- 质量场景库使用独立页面和独立一级导航，不嵌入ITR、彻底解决单或漏测分析详情页；
- 建议固定路由为 `/quality-scenarios`；
- 首要筛选条件为IPMT、SPDT和产品型号；
- 按产品、生命周期、业务活动、质量属性和状态查询；
- IPMT、SPDT和产品型号支持多选、级联和关键词检索；
- 筛选值动态来自彻底解决单和场景资产适用范围，不写死为固定枚举；
- 场景列表显示场景名称、IPMT、SPDT、适用产品型号、生命周期、业务活动、来源问题数、版本和发布状态；
- 场景详情可下钻来源问题；
- 新版本发布后保留历史版本；
- 已发布场景不能硬删除，仅可退役。

### 7.5 场景词典设置

- 建议路由为 `/settings/scenario-taxonomy`；
- 左侧管理生命周期，右侧管理当前阶段下的业务活动；
- 可按IPMT、SPDT、产品型号和启用状态查询适用范围；
- 编辑页展示定义、场景链路、判定证据、正反例和易混淆边界；
- 激活前显示差异预览及受影响的Prompt和产品范围。

## 8. 数据对象建议

独立建立以下对象，不将场景推理字段直接追加到 `source_material.raw_json`：

- `scenario_taxonomy_version`：词典版本；
- `scenario_lifecycle`：标准生命周期；
- `scenario_activity`：业务活动场景；
- `issue_scenario_analysis`：单问题场景分析版本；
- `issue_scenario_evidence`：结论证据；
- `scenario_confirmation`：人工确认与修订；
- `scenario_generation_job`：人工指定的聚类任务；
- `scenario_candidate`：场景候选版本；
- `quality_scenario`：已发布场景主记录；
- `quality_scenario_version`：已发布场景版本；
- `quality_scenario_issue_link`：场景与来源问题关系。

IPMT、SPDT和产品型号属于多值适用范围，不建议在场景表中使用逗号字符串。建议增加 `quality_scenario_scope`，使用 `scope_type = IPMT / SPDT / PRODUCT_MODEL`和 `scope_value` 表达多对多范围，便于准确筛选和后续权限控制。

## 10. 验收条件

1. 每条场景分析都能追溯到CS和漏测分析的具体字段；
2. 问题事实与分析结论的权威来源符合矩阵；
3. 没有漏测分析时，系统不伪造流出原因和能力缺口；
4. 生命周期、业务活动和场景链路均有证据、置信度和候选排除理由；
5. 低置信度分析进入人工确认，确认结果不覆盖AI原始输出；
6. 用户能按产品、时间、IPMT、SPDT和场景分析状态选择问题；
7. 未人工指定范围时不会自动生成场景库；
8. 聚类可查看来源问题、匹配理由和异常点；
9. 人工可合并、拆分、移动问题并修改场景边界；
10. 只有通过人工审核的候选场景可发布；
11. 已发布场景可版本化和退役，不被重新分析覆盖；
12. 现有漏测分析、质量洞察和产品综合报告的默认口径不受影响。
13. 管理员可修改生命周期和业务活动词典，且修改通过新版本生效；
14. 质量场景在独立页面展示，可通过IPMT、SPDT和产品型号准确筛选；
15. 词典新版本不会静默改写历史分析和已发布场景。

## 11. 本期不做

- 不将AI候选场景自动发布；
- 不直接对全量问题一次性聚类；
- 不将 iFA Evolution（PLC）的34个业务活动强行复用到HMI、机器人、硬件和机械问题；
- 不在场景库内复制原始问题全文；
- 不将未经人工确认的候选场景用于正式准入或考核。
