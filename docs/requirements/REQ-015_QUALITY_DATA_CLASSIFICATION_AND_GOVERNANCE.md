# REQ-015 质量问题数据分类与治理

状态：`TRIAGED`

优先级：`P0`

来源：2026-08-31 长期数据规划

## 一、目标

系统将长期接入多种质量问题数据。不同数据的目的、完整度、可信度和适用分析不同，不能继续按同一口径直接混合统计和分析。

需要建立两条相互独立的分类轴：

```text
数据类型：数据从哪里来、质量如何、默认用于什么业务
问题领域：问题属于软件、硬件还是机械
```

数据类型不能代替问题领域，问题领域也不能推导数据可信度。

## 二、第一轴：数据类型

### 1. ITR基础问题数据 `ITR_BASE`

包含两个相互关联的数据对象：

- ITR问题：主要面向现场响应和恢复，描述客户现场现象、影响、临时处置和恢复过程。
- ITR彻底解决单：主要记录进一步定位、根因、彻底解决措施和验证结论。

默认用途：

- 作为基础事实和查询数据。
- 支持按问题编号、产品、客户、时间、现象和措施检索。
- 作为其他专项分析的证据来源。
- 当前不默认承担深度质量能力分析；将来如需专项分析，另立需求和分析契约。

治理要求：

- ITR问题与彻底解决单通过业务问题编号或显式关联键形成同一问题链路。
- 两份记录分别保留原文、来源和版本，不把彻底解决内容直接覆盖现场恢复记录。
- 同一问题链路在统计时不得因两类单据而重复计数。

### 2. 漏测分析数据 `ESCAPE_ANALYSIS`

当前系统的主要分析数据。由开发和测试在原始问题基础上进一步分析，数据质量相对较高。

默认用途：

- 发生原因和流出原因分析。
- MRC分类。
- 生命周期和问题领域识别。
- 质量工程、质量管理和横向治理能力缺口。
- 人工确认、质量洞察和产品综合报告。

默认定位：当前正式分析主数据集。

### 3. 重大问题复盘数据 `MAJOR_INCIDENT_REVIEW`

重大问题通常具有详细复盘材料、会议结论、时间线、影响分析、根因、措施和责任闭环。

默认用途：

- 深度根因和系统性失效机理分析。
- 技术与管理机制联合分析。
- 公司级治理能力和跨产品风险分析。
- 高价值案例库和正向风险评估。
- 标准、流程、门禁和组织改进输入。

这类数据质量通常较高，但复盘材料可能包含多个文档，应支持一个问题关联多份材料和多个证据片段。

### 4. 批量问题数据 `BATCH_MARKET_ISSUE`

影响范围和质量损失较大，但单条内容通常较粗糙，可能存在字段缺失、重复记录和口径不一致。

默认用途：

- 使用REQ-013隔离数据集进行专项分析。
- 识别批量影响、共性失效模式和问题簇。
- 使用REQ-014识别标准缺口和标准候选。
- 在人工评审前不纳入正式质量洞察和公司级指标。

### 5. 测试问题数据 `TEST_ISSUE`

来自研发测试、系统测试、专项测试或测试缺陷管理的数据，不一定已经流入市场。

默认用途：

- 验证阶段问题分布和测试发现能力分析。
- 识别市场问题之前已发现但未闭环、未合入或未拦截的问题。
- 支持测试有效性、缺陷收敛和发布准入分析。
- 与ITR市场问题关联后分析“测试已发现但市场仍发生”的机制。

测试问题的详细分析范围需要根据真实数据字段另行冻结，不能直接套用市场漏测分析契约。

## 三、第二轴：问题领域

所有数据类型都可以独立标记一个或多个问题领域：

- `SOFTWARE`：软件问题。
- `HARDWARE`：硬件、电气、器件和板卡问题。
- `MECHANICAL`：机械、结构、材料和装配问题。
- `CROSS_DOMAIN`：软硬件、机电或多领域协同问题。
- `UNKNOWN`：现有证据不足。

领域支持主领域和关联领域。例如：软件问题可以主领域为 `SOFTWARE`，同时关联 `HARDWARE`，并记录器件和失效原因。

## 四、建议的数据关系

长期建议将“问题”和“材料/记录”分开：

```text
质量问题 Issue
├── ITR现场恢复记录
├── ITR彻底解决单
├── 漏测分析记录
├── 重大问题复盘材料
├── 批量问题记录
├── 测试问题记录
├── AI分析与人工确认
└── 标准候选、治理措施和风险案例
```

同一质量问题可以关联多种材料。数据来源增加时不重复创建多个正式问题，也不丢失每份原始材料的独立版本和证据身份。

## 五、可信度与用途口径

每份记录至少标记：

- 数据类型。
- 原始来源和来源系统。
- 数据质量等级。
- 完整度和必填字段覆盖率。
- 是否经过业务人员确认。
- 是否允许进入正式分析。
- 是否允许进入正式洞察和产品报告。
- 是否仅供查询和证据引用。

建议的默认策略：

| 数据类型 | 默认查询 | 默认AI分析 | 默认正式洞察 | 默认产品报告 |
|---|---:|---:|---:|---:|
| ITR基础问题 | 是 | 否 | 否 | 仅作证据 |
| 漏测分析 | 是 | 是 | 是 | 是 |
| 重大问题复盘 | 是 | 是，使用深度契约 | 是，独立标识 | 是 |
| 批量问题 | 是，数据集内 | 是，隔离分析 | 否 | 仅临时专项报告 |
| 测试问题 | 是 | 按专项契约 | 默认否 | 默认否 |

所有默认值允许通过后续需求和人工审批调整，但必须保留调整记录。

## 六、去重和关联

- 首选ITR业务编号作为关联键，但不能假设所有数据都有统一ITR号。
- 支持显式人工关联和解除关联。
- 缺少统一编号时，可基于产品、时间、客户、现象和版本生成相似候选，但不得自动合并。
- 一个问题链路只能有一个正式主问题标识。
- 同一材料不得被两个问题链路重复占用，除非明确标记为共性证据。
- 统计必须区分“问题数、材料数、记录数和受影响对象数”。

## 七、页面口径

### 全局数据范围

所有分析和洞察页面显示当前数据范围，例如：

```text
数据类型：漏测分析
问题领域：软件 + 软硬协同
正式问题：186
关联材料：241
分析覆盖率：92%
```

### 问题详情

在一个问题详情中查看全部关联材料，并区分：

- 客观事实。
- 现场恢复信息。
- 彻底解决结论。
- 漏测分析。
- 重大问题复盘。
- 测试记录。
- AI推断和人工确认。

### 查询与分析入口

- ITR基础查询保持轻量，优先检索和证据查看。
- 漏测分析继续使用当前主业务流程。
- 重大问题进入深度复盘分析。
- 批量问题进入隔离数据集和标准化专项。
- 测试问题进入测试质量专项，范围另行定义。

## 八、实施顺序

### 第一步：分类与默认范围

- 建立数据类型词典。
- 给当前数据默认标记为 `ESCAPE_ANALYSIS`。
- 为新导入数据选择数据类型和问题领域。
- 正式洞察默认仅使用允许进入正式分析的数据。

### 第二步：ITR问题链路

- 建立主问题与多类材料关联。
- 接入ITR现场恢复和彻底解决单。
- 完成查询、关联和去重，不立即扩展深度分析。

### 第三步：专项流程

- 重大问题深度复盘。
- 批量问题隔离与标准化分析。
- 测试问题专项分析。

## 九、当前明确不做

- 不立即对ITR和彻底解决单增加新的AI深度分析。
- 不把所有数据导入同一正式洞察口径。
- 不用数据类型自动推断软件、硬件或机械领域。
- 不因增加材料类型而复制现有正式问题。
- 不在分类框架未冻结前重写当前稳定问题工作台。

## 十、验收条件

1. 五类数据能够明确区分并显示数据范围。
2. 软件、硬件、机械与数据类型相互独立。
3. ITR现场恢复与彻底解决单可关联为同一问题链路。
4. ITR基础数据可查询但默认不污染正式洞察。
5. 当前漏测分析数据保持现有分析、人工确认、洞察和报告流程。
6. 重大问题、批量问题和测试问题各自使用匹配的数据质量与分析策略。
7. 统计可以区分问题数和材料记录数，避免重复计数。
8. 未来新增数据类型时不需要再次改写核心问题模型。
